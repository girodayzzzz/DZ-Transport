# Database schema

Apply the ordered SQL migrations in `supabase/migrations`. The PostgreSQL API is the authorization boundary for the portal. Mutations with business rules use transactional RPCs with fixed search paths and explicit execution grants. The base customer role derives from a confirmed Auth user. Partner and administrator grants reside in `user_roles` and are never writable by the account holder.

| Records | Access and relationships |
| --- | --- |
| profiles, user_roles | Own profile and grant visibility. Profile edits permit only the display name. Trusted SQL assigns administrator grants. |
| companies, partner_applications | A confirmed account may apply once and read its company and decision. A step-up verified admin manages review, coverage and suspension. |
| transport_inquiries, inquiry_items | An owning customer or step-up admin may read. References are generated by the database. An approved carrier sees a separately written opportunity without direct inquiry access. |
| transport_opportunities | Admin invites a specific approved carrier with a minimal brief. The carrier sees only invitations addressed to them. |
| transport_quotes, quote_costs | A carrier sees its own carrier quote. The customer sees published customer-facing offers. Costs are in a separate admin-only table. |
| transport_orders, transport_assignments | Acceptance creates one order transactionally. A verified administrator explicitly assigns one approved partner, who sees only its own assignment instructions and order history. |
| transport_status_history, notifications | Status changes append history. Notifications are scoped to recipients, with administrator events requiring step-up verification. |
| internal_notes, audit_logs, account_deletion_requests | Notes and audit events require administrator MFA. An account can create and read its own deletion request. |
| dz_private.guest_receipts | Private guest payload, hashed network key and unique validated client reference. The service role invokes the intake RPC. Administrators retrieve guest details through a checked RPC. |

Inquiry and quote rows serialize changes via row locks. The order, quote and assignment constraints protect against conflicting mutations. Quote amounts and costs use bounded integer minor units. SQL aggregates cover completed orders per currency and round margin percentages using numeric arithmetic. The manager displays amounts as stored, with currency and VAT treatment. The ledger is operational and requires accounting review before use for invoicing.

Guest ownership is never inferred from email or a reference. Guest inquiries remain unlinked. Account claiming, document storage policies, multiple carriers on one order, re-quotation after withdrawal and automated accounting are future work. The manager’s working lists and client-side filters currently use the latest 100 results per query. Dashboard counts and financial aggregates run over all authorized records.

Archiving is reversible operationally through trusted SQL. The private purge function and the deletion-request workflow require an approved retention and legal-hold review. Foreign keys cascade or clear ownership according to record type. See [Backup and restore](BACKUP-AND-RESTORE.md).

Migration `202611260005_customer_onboarding.sql` adds customer classification, registered business name when applicable and a completion timestamp to `profiles`. Existing profiles keep null onboarding columns until the customer enrolls. The V3 profile RLS remains in place. Confirmed users can choose an account classification and complete free onboarding through owner-scoped RPCs. The RPCs leave role grants and partner approval independent. Completion is retry-safe and the selected classification is locked after completion.

For application rollback, disable `PUBLIC_DZ_CUSTOMER_ONBOARDING` and rebuild. The migration is additive and can remain applied with the existing application. Preserve recorded classifications in backups before considering any later schema removal.

## Quick Deal

Migration 006 centralizes assignment under an inquiry and carrier role lock. Migration 007 adds `dz_private.quick_deal_settings`, `quick_deals` and `quick_deal_candidates`. The inquiry foreign key is unique and candidates are unique per deal and carrier. All tables use RLS with direct access revoked. Public RPCs authorize and project the workflow. The [Quick Deal guide](QUICK-DEAL.md) describes reservation expiry and the carrier-visible fields.
